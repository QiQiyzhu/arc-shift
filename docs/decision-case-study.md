# ARC//SHIFT：候选检查减少，为什么仍然不能宣布优化成功？

[打开可交互实验](https://arc-shift.black-kid-3047.chatgpt.site/lab/#arc) · [原始性能报告](performance-v2.md) · [完整 A–T 手册](interview-dossier.md)

## 要做的决定

高速弹体与大量移动敌人使全量几何检查变贵。是否应该用空间网格缩小候选集？判断顺序是：先证明行为等价，再测净成本，最后观察玩家实际看到的帧时间。三个门槛不能相互替代。

本轮新增独立的 `/lab/` 入口，直接复用游戏中的 [UniformGrid 与 sweptAABB](../src/core/spatial-grid.ts)、[segmentHits](../src/combat/rules.ts) 和固定种子 Random。实验不实例化 World、不触发游戏命令、不读写存档；改变的是独立夹具中的坐标和查询参数。它是实时几何对照，不是新的整局性能测量。

## 两个能立刻复现的反例

1. 默认分散布局下勾选“故意只查询终点”。候选更少，但高速路径中间的目标被漏掉。将最终精确几何判断做得再正确，也补不回候选阶段已经筛掉的目标。
2. 切换跨格击退，勾选“不更新击退后的索引”。对象的新坐标正确，格子里的成员关系却仍在旧位置。引用同一个对象不能替代索引失效和更新策略。

关闭错误开关后，索引命中 ID 与顺序应重新匹配全量遍历。密集布局则显示另一种结果：可以完全正确，却几乎筛不掉候选。此时维护、去重与排序会占成本，不能由数据结构名称推出性能结论。

[实验测试](../tests/decision-lab.test.ts) 用三种布局、三种格长和 24 个种子检查命中顺序，还独立检查错误实现确实被反例拒绝。完整战斗语义的 oracle 仍在 [spatial-grid.test.ts](../tests/spatial-grid.test.ts)，小实验没有替代它。

## 已经测过的成本与失败

| 250 敌人固定夹具 | 之前 | 首版索引 | 修正后 |
|---|---:|---:|---:|
| Node 规则层 P95（ms） | 1.8786 | 4.135 | 1.0712 |

首版减少了几何测试，却因为频繁移除/重插格子、重新分配/排序而退化。修正保留格子占用边界，仅在跨格时更新候选，并维持源数组顺序。既有固定 tick 对照的敌人位置、HP、总伤害和 RNG 状态一致。

同轮真实浏览器里，250 敌人 P95 帧时间却从 **76.4 升到 83.3 ms**。绘制、调度、GC 和夹具时间推进都与 Node 不同；短时并发采样还限制因果归因。它只证明这次规则层夹具的改善，不证明稳定 60 FPS 或普遍的渲染加速。

## 为什么保留简单全量遍历

全量实现承担独立对照和小负载基线。网格只负责保守召回，精确判断沿用原规则。穿透先后会影响伤害、RNG 消耗与后续状态，所以需要保持源数组顺序，而不只是 Set 相等。

没有把寻敌、链反应和近战全都改成索引。先找出热路径，避免把未测量的复杂度扩大。极端聚集、巨大地图或物体尺寸悬殊时，应带着同一 oracle 比较其他结构。

## 下一实验如何改变决定

固定相同 tick 和负载，分别记录索引维护、候选收集、精确几何、绘制与分配成本；在隔离机器上多次测量浏览器帧时间。预先声明退化场景与可接受误差，保留所有失败记录。只有净成本与真实场景同时支持时，再扩大使用范围。

游戏战斗核心没有接云端 LLM：网络抖动、费用和不可复现输出不适合作为每帧碰撞或数值规则。AI 辅助开发与实时游戏逻辑是两件事。
